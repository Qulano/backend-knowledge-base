1. Big(O) - нотация которая позволяет определить как быстро устанет наш процессор и как быстро оперативная память забьется при работе с        огромным потоком даных

    O(1) - Постоянное время
    Аналогия: чтобы узнать сколько времени нужно всего лишь посмотреть на часы, внешние факторы никак не влияются на значение
    Пример: доступ по ключу с словаре dict[key] или проверка x in my_set

    O(N) - линейное время, движемся поэтапно
    Аналогия: ищем ключи по карманам в гардеробе, нужно будет проверить N-курток (10 круток - 10 проверок, 1000 курток - 1000 проверок)
    Пример: поиск элемента в списке x in my_list или цикл for item in items

    O(N^2) - Квадратичное время (исследуем попарно)
    Аналогия: Каждый гость на вечеринке жмет руку каждому гостю
    Пример: Вложенный цикл for внутри цикла for или поиск по списку внутри другого цикла, это самое ужасное что может произойти в работе программмы, нужно изначально все продумывать так, чтобы такого не случилось


2. Память и потоковая обработка

    Изначально есть проблема чтения файлов целиком при использваонии (read(), readlines(), pandas.read_csv()):
    Весь файл полностью загружается в оперативную память RAM разом
    При обработке файла на 25 ГБ на сервере с 4ГБ RAM операционная система активирует OOM KILLER (Out-of-Memory Killer)
    который принудительно убивает процесс Python с ошибкой SIGKILL.

    Инженерное решение:
    Построчное чтение через генераторы (for line in file / csv.reader).
    В памяти находится только одна строка, которую мы проверяем и очищаем и так далее (почти не занимает память)
    в таком случае рсход памяти у нас констатный равный O(1), скрипту все равно сколько весит файл, сервер будет работаь без проблем


3. Проверка дубликатов: Списки(list()) против Множеств(set())

    Ловушка списков(list.append)
    Проверка if id in seen_ids переберает все элементы этого списка (Цикл - сложность O(N)), так как мы проверяем каждую строку то мы приходим к вложенному циклу(Сложность - O(N^2)), На больних данных скрипт упадет

    Решение через множества (set.add)
    set реализован как хэш-таблица  
    провер if id in seen_ids в множестве работает O(1) - мгновенно, поэтому весь файл обрабатывается за линейное время O(N)

    Примечание, при размере большом размере файла множества просто захлебнуться (O(N)) поэтому есть два пути
    1. Жертвуем точность но выигрываем в скорости, исползуя ФИЛЬТР БЛУМА - супер легкая структура данных, которая занимает очень мало места в памяти и говорит: элемента ТОЧНО или ВОЗМОЖНО присутсвует.
    Аналогия: Охранник на входе в клуб с идеальной зрительной памятью на лица, но без блокнота.
    Если подошел незнакомец — охранник скажет: «Этого человека тут ТОЧНО НЕ БЫЛО» (100% гарантия, никаких ложных пропусков).
    Но из-за темноты он иногда может обознаться и сказать: «Хм, кажется, я тебя уже видел», хотя человек пришел впервые (небольшая погрешность, ложноположительное срабатывание).

    2. Добиваемся максимальной точности, но сильно проигрываем в скорости External Merge Sort - файл разбивается на маленькие куски, которые сортируются в памяти, сохраняются на диске, а потом опять объединяются
    Аналогия: У тебя на полу гора из 1 000 000 разбросанных карточек, а на маленьком столике помещается только 100 штук.
    Что ты делаешь? Берешь по 100 штук, раскладываешь по алфавиту на столике и складываешь аккуратными стопочками обратно на пол. А потом просто берешь верхние карточки из стопочек и объединяешь в одну идеальную линию.


4. Как устроена хэш-таблица

    Принцип работы: 
    Ключ передается в функцию hash() вычисляется число по этому числу процессор мгновенно обращается к конкретной ячейке памяти (вешалке в гардеробе). Поиск происходит в 1 шаг без перебора элементов O(1).

    Неизменяемость ключей (Immutable):
    Ключом словаря или элементом множества могут быть только неизменяемые типы данных (str, int, tuple). 
    Список list положить нельзя, потому что если список изменится, его хэш изменится, и объект потеряется в памяти.

    Коллизия:
    Ситуация, когда два разных объекта случайно выдали одинаковый хэш. Python умеет разрешать такие конфликты внутри сам.

    Динамическое расширение:
    Когда хэш-таблица заполняется примерно на 2/3, Python автоматически выделяет новый кусок памяти побольше, чтобы поиск всегда оставался быстрым O(1).

7. B-tree индексы под капотом PostgreSQL

    Без индекса (Seq Scan - Sequential Scan):
    База данных честно перебирает каждою строчку на диске от первой до последней
    Сложности по времени O(N). На миллионах записей запросы висят секундами

    С B-Tree индексом (Index Scan):
    B-Tree (Balanced Tree - Сбалансированное дерево): Структура данных в виде разветвленного дерева.
    Принцип работы: Похож на игру "Угадай число": каждый шаг делит оставшиеся варианты пополам (больше/меньше).
    Среди 1 000 000 записей точное значение находится всего за  ~ 20 шагов
    Сложность по времени: O(logN) (логарифмическое время - практически мгновенно)
    Суперсила B-Tree: В отличие от хэша, умеет быстро искать диапазоны ("<", ">", "BETWEEN") и делать сортировку ("ORDER BY")

    Почему нельзя вешать индексы на каждую колонку (столбец)?
    1. Расход памяти: Каждый индекс это отдельная тяжелая структура на диске и в RAM.
    2. Замедление записи (`INSERT`, `UPDATE`, `DELETE`): При добавлении одной новой строки база обязана не просто записать её, но и перестроить ветки во ВСЕХ существующих индексах. Много индексов = медленная вставка данных.
    Правило инженера: Индекс создается только на колонки, по которым часто идет поиск (`WHERE`) или объединение (`JOIN`)


8. Тестирование CLI программ и паттерн AAA (PyTest)

    Проблема CLI программв тестах:
    Пограмма с циклом `while True` и функцией `input()` ждут ввода человека с клавиатуры. В автоматических тестах PyTest такой скрипт просто зависнет намертво.

    Два встроенных супер-инструмента PyTest:
    1. `monkeypatch` - подменяет стандартные функции Python. Мы подменяем системный `builtins.input` на заранее заготовленных список строк, чтобы программа брала данные автоматически 
    2. `capsys` - "видеокамера над терминалом". Перехватывает весь текст, выведенный через `print()`, чтобы в конце проверять его через `assert`


    Золотой стандарт индустрии: Паттерн AAA (Arrange - Act - Assert)
    Любой тест в мире строится по 3 фазаам:

    1. Arrage (Подготовка До)
        Готовим тестовые данные, подделываем ввод через `monkeypatch` или создаем тестовые записи в БД
    2. Act (Действие Во Время)
        Запускаем целевую функцию: вызываем `run_calculator` или `client.get()`.
    3. Assert (Проверка После)
        Сверяем полученный результат с ожиданиями c помощью команды `assert`

    Архитектурный вывод
    Код должен быть спроектирован так, чтобы его было легко тестировать. Бизнес-логику лучше выносить в чистые функции без `input()` и `print()`
    а цикл ввода делать лишь тонкой оболочкой


9. Транзакция и 4 суперсилы ACID (PostgreSQL)

    Что такое транзакция базе данных?

    Аналогия из жизни: отправляю деньги своему другу, на твоем счете они списываются а на его счете они прибавляются, что если вдруг сервер внезапно упадет, деньги списали и не перешли на другой счет, по итогу они просто улетели в пустоту, чтобы этого избежать требуется зафиксировать выполнение всех действий - транзакцию

    Транзакция - это контейнер, в который мы заворачиваем SQL команды.

    Работает по правилу "ВСЕ ИЛИ НИЧЕГО" (All-or-Nothing)

    Два исхода:
    `COMMIT` - все прошло успешно, запечатать и сохранить изменения в базу намертво
    `ROLLBACK` - произошла ошибка, удалить контейнер и откатить базу до исходного состояния


    Четыре суперсилы транзакции - ACID

    1. A - Atomicity (Атомарность):
    Суть: Транзакция неделима, как атом. Либо все, либо ничего
    Пример спасения: Скрипт вставляет в базу строки, вдруг попадается битая строка, база возвращается к исходному состоянию (ROLLBACK), в таблице БД не остается огрызков

    2. C - Consistency (Согласованность / Непротиворечивость):
    Суть: Нельзя нарушать правила базы данных
    Пример: БД никогда не даст сохранить заказ без существующего клиента, отрицательную цену или пустую строку там, где стоит ограничение
    NOT NULL

    3. I - Isolation (Изоляция):
    Суть: Одновременные операции тысячи пользователей не путают друг друга
    Защита от Race Condition (состояние гонки): Если два человека в одну минуты жмут "Купить" на последний товар на складе, база изолирует их процессы. Первый купит товар, а второму база ответит: "Товар закончился". Товар не продастся дважды

    4. D - Durability (Долговечность / Надежность):
    Суть: если БД ответила `COMMIT`, данные гарантированно записаны на жесткий диск (в специальный журнал WAL).
    Даже если через пару милисекунд сервер вырубит - после выключения данные не пропадут


10. Docker: Персистентность данных и Volumes (Тома)

    1. Проблема эфемерности контейнеров:

    Контейнер по умолчанию одноразовый. Все изменения пишутся во временной слой (writable layer)
    Если база данных PostgreSQL запущена без `volumes`, то при выполнении команды `docker compose down` контейнер уничтожается вместе со всеми данными, таблицами и индексами без возможности восстановления

    2. Что такое Docker Volume (Аналогия: Внешний SSD / Флешка)
    Контейнер это арендованный ноутбук 
    Volume - внешний диск, лежащий на сервере
    Мы пробрасываем провод (монтируем) внутреннюю папку базы данных (`/var/lib/postgresql/data`, где лежат таблицы и WAL-логи) на реальный диск хоста.

    3. Результат:
    База пишет данные напрямуб на сервер
    При `docker compose down` «ноутбук» утилизируется, но внешний диск с данными остается целым на хосте.
    При следующем `docker compose up` новый контейнер мгновенно подключается к существующему диску, и все данные на месте.


11. Высоконагруженный Data API: FastAPI, Redis, Alembic и метрики

    1. Асинхронность (Event Loop) и async/await:

    Аналогия с рестораном: 1 официант (1 ядро CPU / Event Loop) и повар (I/O: база данных, диск, сеть).
    официант отдает заказ на кухню `await` и будет обслуживать других клиентов, не простаивая в ожидании готовности блюда.
    Конкурентность без блокирования потока

    2. Connection pool (Пул соединений) в asyncpg:

    Создание соединений с нуля дорогое: TCP 3-Way Handshake + аутентификация + `fork()` отдельные процессы в PostgreSQL
    с выделением памяти.
    Пул соединений держит 10-20 уже открытых и авторизованных соединений (служебные такси). Запрос берет свободное соединение (`acquire`),
    быстро делает запрос и возвращает обратно (`release`). Задержка на подключение = 0 мс

    3. Redis и паттерн Cache-Aside (Кэш на обочине)

    Cache Hit: Нашли ключ в Redis отдали за 1-2 мс из RAM.
    Cache Miss: Данных нет тяжелый расчет в PostgreSQL сохранили в Redis в формате JSON c временем жизни (TTL)
    Зачем нужен TTL: экономия дорогой оперативной памяти и защита от протухания данных(Stale Data)

    4. Миграции баз данных (Alembic):

    Это Git для структуры таблиц. Исключает ручные правки на сервере.
    В PostgreSQL создается таблица `alembic_version`, где хранится текущий  хэш ревизии.
    Команды `alembic upgrade head`(накатить до последней) и `alembic downgrade`(безопасный откат).

    5. Метрики нагрузки (Locust):
    RPS (Requests Per Second): Сколько запросов в секунду бэкенд успевает полноценно обработать. В нашем проекте: 318 RPS
    Перцентили P95 / P99 против среднего (Average):
    Среднее время ответа врет (средняя температура по больнице), маскируя единичные зависшие запросы
    P95: 95% всех пользователей получили ответ быстрее этого порога (только 5% ждали дольше). Это главный ориентир в SLA и High-Load


12. Docker Network (DNS) и Логирование (Loguru)

    1. Docker Network и внутренний DNS
    Каждый контейнер полностью изолирован и имеет свой собственный `localhost` (127.0.0.1)
    FastAPI не может подключиться к базе через `localhost`, так как Postgres находится в другом изолированном контейнере
    Docker Compose автоматически создает общую подсеть и поднимает Embedded DNS Контейнеры находят друг друга по имени сервиса из файла YML (например, `postgres:5432`)

    2. Логирование через Loguru (почему не print()):
    Уровни критичности: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` позволяют фильтровать поток событий и настраивать алерты
    Контекст ошибки: автоматически сохраняет точно время с милисекундами, имя модуля, функции и номер строки
    Ротация и очистка (Rotation & Retention): предотвращает переполнение диска сервера (авто-нарезка логов по 10 МБ и удаление старых через N дней)


13. Объектно-оринентированное программирование (ООП) в Python

    1. Класс и объект (Формочка и Печенье):
    Класс (Class) Формочка. Определяет структуру поведения
    Объект (Instance) Конкретно печенье, выдавленное из теста. Занимает физическое место в оперативной памяти (RAM)
    `__init__` (Инициализатор): Метод (роддом объекта), который автоматически вызывается в момент создания и задает обязательные стартовые атрибуты
    `self`: Указатель на этот конкретный экземпляр в памяти. 

    2. 4 Столпа ООП:

        1. Инкапсуляция (Encapsulation)
        Объединение данных и методов работы с ними в отдельную "капсулу" (класс)
        Сокрытие внутреннего состояния: Защита данных от прямого вмешательства извне. Объект сам контролирует свои свойства через методы
        Обработка некорректных данных: Если передавать некорректное значение, метод должен перехватывать ошибку на входе, предотвращая повреждения данных в системе

        2. Наследование (Inheritance):
        Механизм создания ноаого класса на основе существующего без копирования кода (принцип DRY - Don't Repeat Yourself).
        Класс-наследник получает все методы и свойства родителя, но может добавлять свои уникальные.
        `super()` Вызов методов родительского класса, чтобы дилигировать базовую настройку отцу
        
        3. Полиморфизм (Polymorphism)
        Буквально: "Множество форм одного действия"
        Единый интерфейс у разных объектов с совершенно разной внутренней реализацией
        Позволяет обрабатыать разнородные объекты в одном цикле без бесконечных проверок `if / elif `
        Duck Typing (Утиная типизация в Python) Если крякает как утка - значит утка. Python не требует общего предка, главное, чтобы у всех физически присуствовал нужный метод

        4. Абстракция (Abstraction)
        Выделение существенных характеристик объекта и отсечение второстепенных.
        Абстрактный базовый класс (ABC): Класс-контракт из которого напрямую нельзя создать объект
        Через `@abstractmethod` на уровне архитектуры жестко фиксирует конракт: обязывает всех разработчиков реализовать конкретные методы в классах-наследниках под угрозой запрета запуска программы


14. Dunder методы в Python

    Dunder - это метод с двоийным подчеркиванием (`__name__`), которые перегружают стандартное поведение встроенных операторов и функций Python.

    1. Отображение объектов: `__str__` против `__repr__`
        `__str__` (Чек для покупателя):
        Пользовательский красивый вид: Вызывает функциями `print(obj)` и `str(obj)`.
        `__repr__` (Технический чертеж для разработчика):
        Точное, однозначное представление для отладки. Вызывается при отображении списков `[obj1, obj2]`, в логах и интерактивной консоли

# Функциональный Python, Декораторы и ООП Pro
1.  Функции как объекты первого рода (First-Class Citizen)

Аналогия: В Python все является объектом в оперативной памяти (RAM). Функция - это не высеченная на стене инструкция, а обычная флешка с рецептом, которую можно перекладывать, хранить и передавать другим

4 Суперсилы функции как объекта
1. Присвоить переменной (наклеить второй ярлык на тот же объект в памяти)
2. Хранить в структурах данных (списки, словари - паттерн "Словарь-дипетчер" с безлопаснм `.get()`).
3. Передать аргументом в другую функцию (Callback - функция обратного вызова)
4. Объявить внутри другой функции и вернуть наружу

Критическая разница (`func` и `func()`)
`func` (без скобок) - ссылка на сам объект функции в памяти
`func()` (со скобками) - оператор вызова ("кнопка пуск") Если случайно поставить `()` там, где нужна ссылка (или вызвать строку/словарь), получим `TypeError: .... object is not callable`
Термины маркеры: First-class citizen, Higher-Order Function (ФПВ - принимает или возвращает функцию), Сallback, `callable`


2. Область видимости (Scope) и правило LEGB

Порядок поиска имен в Python (LEGB):
`L`ocal - внутри текущей функции
`E`nclosing - В области видимости внешней функции - родителя
`G`lobal - на уровне всего файла (модуля)
`B`uilt-in - встроенные имена Python
Ловушка `UnboundLocalError`: Как только Python внутри функции присваивание (`=` или `+=`), он заранее помечает имя как новую локальную переменную и перекрывает ей ндноименные переменные снаружи.
Правило безопасности: никогда не называть локальные переменные именами импортированных модулей (`time`, `random`) или встроенных функций (`list`, `sum`, `str`)


3. `*args` и `**kwargs` (Успаковка и распаковка)

Аналогия: Универасальный переходник. `*args` - рюкзак для безымянных вещей, `**kwargs` - органайзер с ярлычками. Вся магия в звездочках `*` и `**`, сами слова `args` и `kwargs` просто традиция

Упаковка (в заголовке `def`):
`*args` собирает все лишние (позиционные) аргументы в `tuple` (кортеж)
`**kwargs` собирает все лишние (именованные аргументы) (`key=value`) в `dict` (словарь)
Распаковка (при вызове функции): звездочки перед списком/кортежем (`*bag`) или словарем (`**bonus`) вытряхивает их элементы обратно в обычные позиционные и именованные аргументы
Строгий порядок параметров в `def`:
1. Обычные парметры
2. `*args` 
3. Keyword_only параметры (стоят после `*args`, передаются строго по имени)
4. `**kwargs`
Зачем применяют в продакшене: когда число аргументов заранее неизвестно (декораторы-обертки, `print`) и для транзитного проброса аргументов дальше в другую функцию или родительский класс
Термины-маркеры для собеса: Positional vs Keyword arguments, Argument Packing & Unpacking


4. Замыкания (Closures) и `nonlocal`
Аналогия: функция с рюкзаком памяти (`__closure__`). Внешняя функция-фабрика уже отработала и закрылась, но возвращенная внутренняя функция упаковала нужные ей внешние переменные в свой личный рюкзак и унесла с собой

3 Обязательных условия Замыкания:
1. Есть внешняя и вложенная функции.
2. Вложенная функция ссылается на переменную из Enclosing scope (внешней функции)
3. Внешняя функция возвращает вложенную функцию как объект (без `()`)
Зачем нужно: Позволяет одной фабрике создавать сколько угодно независимых функций с собственным изолированным состоянием (вместо дублирования однотипных функций)
Зачем `nonlocal`: Читать переменные из рюкзака можно свободно, но попытка изменить неизменяемую переменную вызывает `UnboundLocalError`. Ключевое слово `nonlocal` указывает Python: Не создавай новую локальную переменную, измени именно ту, что лежит в рюкзаке внешней функции


5. Декораторы (`@decorator` и `@functools.wraps`)

Аналогия: Подарочная обертка. Реализация принципа Open/Closed (SOLID): расширяем поведение функции (замер времени, логирование, кэш, проверка прав) ДО и ПОСЛЕ ее выполнения, не меняя код внутри самой функции

Механика работы:
Декоратор - это ФВП, принимающая целевую функцию `func`
Внутри объявляется обертка `wrapper(*args, **kwargs)`, которая выполняет логику ДО, вызывает `result = func(*args, **kwargs)` (распаковывая аргументы), выполняет логику ПОСЛЕ и обязательно возвращает `result` (иначе декорированная функция начнет возвращать None)
Декоратор возвращает объект `wrapper` (без скобок)
Синтаксический сахар: `@timer` над функцией `summer` эквивалентен подмене `summer = timer(summer)`
Зачем `@functools.wraps(func)`: Без него декоратор подменяет метаданные оригинальной функции на `wrapper` (`__name__`, `__doc__`), что ломает логи, Pytest и маршрутизацию в FastAPI. `@wraps(func)` над `wrapper` подклеивает паспорт с оригинала на обертку


6. ООП со звездочкой

1. Вызываемые объекты (`__call__`)
Реализация dunder-метода `__call__(self, ...)` позволяет вызывать экземпляр класса со скобками `()` как функцию (`callable(obj) == True`).
Замыкания vs Класс с `__call__`: Когда логика и состояния разрастаются, клас удобнее замыкания с кучей `nonlocal`: все данные чисто лежат в `self`, их можно читать снаружи и дополнять методами, сохраняя при этом вызов `obj(...)`.
Где встречаются: декораторы в виде классов, ML-модели (PyTorch), зависисимости FastAPI (`Depends`)

2. `@classmethod` vs `@staticmethod`
Обычный метод (`self`) работает с кокретными объектами (печеньем)
`@classmethod` (`cls`): первым параметром получает ссылку на сам класс (формочку). Главное применение - альтернативные конструкторы / фабричные методы (`from_string`, `from_dict`, `from_json`). Корректно работает при наследовании, создавая экземляр того класса, от котрого вызван.
`@staticmethod` (без `self` и `cls`): обычная независимая функция-утилита (калькулятор на полке пекарни), помещенная внутрь класса для логической группировки.
Правило чистого кода: методы `is...` обязаны возвращать строго чистый `bool` (а не кортеж с сообщениями), так как любой непустой кортеж в условиях `if` оценивается как `True` (Truthy)

3. Транзитный проброс в родителя (`super().__init__(*args, **kwargs)`)
Защищает дочерний класс от хрупкости, чтобы не дублировать длинный список параметров родителя в каждом наследнике.
Новые параметры наследника размещают между `*args` и `**kwargs`со значением по умолчанию: позиционные аргументы родителя уходят в `*args` без сдвига порядка, а параметр наследника передается строго по имени (keyword-only)

4. Контекстные менеджеры (`__enter__` и `__exit__`)
Аналогия: Дверь с автодоводчиком / Страховочный шлюз (под капотом работает как `try ... finally`). Гарантирует освобождение ресурсов (закрытие файлов, возврат коннекта в пул БД, `ROLLBACK` транзакции), даже если внутри блока `with` упало исключение

`__enter__(self)`: срабатывает при входе в блок `with`; то, что возвращает `return`, попадает в переменную `as`.
`__exit__(self, exc_type, exc_val, exc_tb)`: срабатывает всегда при выходе из блока `with`.
Если ошибок не было - во всех трех параметрах лежит `None`
Если внутри блока `with` случилась ошибка - сюда передается тип, объект и traceback исключения (можно безопасно откатить транзакцию и закрыть соединение).
Ловушка `return True` в `__exit__`: Если `__exit__` вернет `True`, менеджер подавит, проглотит ошибку, внешний код, (включая внешний `with` и `try/except`) не узнает об аварии. В продакшене обычно возвращает `None`/`False`, оставляю обработку исключений внешнему `try ... except`.


# Итераторы, Генераторы, `yield` и Comprehensions под капотом

1. Зачем это нужно в Data Engineering и Backend?
В продакшене файлы и потоки строк из БД могут весить десятки гигабайт. Загрузка их целиком в `list` приводит к сложности O(N) по памяти и падению процесса от (SIGKILL)
Решение Lazy Evaluation (ленивые вычисления): данные читаются, фильтруются и выдабтся строго по одному элементу в момент запроса, удерживая потребление RAM на уровне O(1)

2. Что такое итератор и итерируемый объект? (Протокол итерации)
Физическая аналогия: Книга (`Iterable`) и закладка с курсором (`Iterator`).

Итерируемый объект (Iterable) - это коллекция или источник данных по которому можно пройтись циклом (`list`, `str`, `tuple`, `set`, `dict`, `range`)
Он хранит данные, но не помнит на каком элементе остановилось чтение.
В Матрице Python у него обязан быть метод `__iter__`, который при вызове встроенной функции `iter(obj)` - создает и выдает новую закладку (новый итератор)
По одному и тому же итерируемому объекту можно пройтись циклом `for` сколько угодно раз.

Итератор (Iterator) - это специальный объект-курсор (одноразовый конвеер), который не храни всю коллекцию целиком, а запоминает лишь текущее состояние (позицию) и умеет по запросу выдавать строго следующий элемент
Обязательные методы итератора (протокол итерации):
`__next__` - возвращает следующий элемент и сдвигает указатель вперед. Когда элементы заканчиваются, выбрасывает специальное исключение `StopIteration` (штатный сигнал тормоза, а не ошибка)
`__iter__` - возвращает самого себя (`self`) чтобы итератор тоже можно было передать в цикл `for`
Главное свойство: итератор одноразовый. Перемотать его назад - нельзя после выброса `StopIteration`, при люых повторных запросах он остается пустым.

Золотое правило для собеседования:
Любой Iterator является Iterable (потому что есть метод `__iter__` - возвращающий (`self`))
Не любой Iterable является Iterator(отсутствует метод `__next__`)
Если у кастомного класса-итератора убрать `__iter__` то ручной `next(obj)` сработает, а цикл `for` упадет с ошибкой `object is not iterable`

Как цикл `for` работает под капотом (без индексов) 
1. Один раз перед началом цикла вызывает `iter(объект)`, получая итератор
2. Запускает бесконечный цикл While True
3. Внутри блока try вызывает `next(итератор)`, получая слудующий элемент
4. Когда прилетает `StopIteration` блок `except` обрабатывает искючение и делает `break`

3. Генераторы и ключевое слово `yield`
Генератор - это ленивый одноразовый итератор, который в Python автоматически создается из обычной функции с помощью ключевого слова `yield`

`return` против `yield`:
`return` (Увольнение с концами) - возращает значение и полностью уничтожает локальный стек функции (все локальные переменные стираются)
`yield` (Кнопка Паузы): отдает значение наружу и замораживает выполение функции, сохраняя все ее локальные переменные и точку остановки. При следующем `next()` выполение продолжается сразу со строчки после `yield`. Код вся функция доходит до конца, Python автоматически выбрасывает `StopIteration`

Важный нюанс: вызов генераторной функции не запускает ее тело! Он лишь создает и возвращает `<generator object>` который ждет первого `next` или цикла `for`.

4. Comprehensions и Generator Expressions
list `[....]`, Set `{....}`, Dict `{k: v ...}` Comprehensions: компактно собирают готовую коллекцию сразу в RAM. Работает быстрее обычного цикла `for` с `.append()`, так как в байт-коде CPython используется оптимизированная инструкция (`LIST.APPEND`) без лишнего поиска метода на каждой итерации.

Порядок нескольких `for` внутри comprehensions: читаются строго слева направо как вложенные циклы (первый `for` - внешний, второй - внутренний). В `dict comprehension` вложенные циклы могут незаметно перезаписывать значения совпадающих ключей
Главная ловушка скобок `(....)` круглые скобки создают не `tuple comprehension`(Его в Python несуществует), а `Generator Expression` - ленивый одноразовый генератор в одну строчку 

Битва памяти (`sys.getsizeof`):
Список на 1млн чисел весит ~8МБ (и это только массив указателей! на 100млн чисел это 800МБ только пож массив указателей и ~3.5 ГБ реально в RAM со всеми объектами `int`)
Выражение-генератор на 1 млн и на 100 млн чисел весит одинаково - ~200 байт (O(1) - по памяти)
Ограничения генераторов: нельзя узнать длину через `len()`, нельзя обратиться по индексу `[0]`, нельзя пройти дважды.

5. Встроенные ленивые итераторы, `yield from` и ETL - пайплайны
`zip(stream_1, stream_2)`: ленивый итератор, который попарно склеивает элементы из нескольких потоков в кортежи и останавливается по самому короткому потоку
`enumerate(stream)`: ленивый итератор, выдающий пары `(индекс, элемент)` - правильная замена костылю `range(len(...))`
`yield from` (Делегирование генераторов): передает управление (поток исполнения) напрямую вложенному итератору или подгенератору без цикла-посредника `for x in sub: yield x`.
Аналогия: открытая дверца холодильника - отдает ингредиенты по одному напрямую потребителю, не перекладывая их руками курьера.
Где незаменимо: рукурсивная распаковка вложенных структур любой глубины и разбиение больших генераторов на модули (отдельные функции)
Генераторный ETL - пайплайн (Два спящих повара)
Стыковка генераторов (`stream = ... `, `pipeline = ...(stream)`) не обрабатывает данные и не тратит память
Конвеер оживает только тогда, когда потребительно циклом `for` тянет элементы по одному: сигнал `next()` пробегает снизу вверх по цепоче и и вытягивает строго по одному элементу (O(1) по памяти для stateless - операций)
Оговорка: генератор не отменяет рост памяти для stateful - операций (дедупликация через `set()`, полная сортировка), а случайный вызов `list(pipiline)` - убьет всю ленивость

6. Ловушка модификация списка во время итерации
Нельзя удалять элементы из списка (`.remove()`, `del`) прямо внутри цикла `for` по этому же списку. Внутренний итератор списка шагает по индексам `0,1,2,3 ... `: при удалении элемента хвост списка сдвигается влево, и следующий элемент о стает на уже проверенный индекс - поэтому цикл его пропускает
Правильное решение: создать новый отфильтрованный поток через list comprehension или генераторный пайплайн (либо в крайнем случае итерироваться по копии)

7. Шпаргалка

Что такое итератор и чем он отличается от iterable? Iterable - это коллекциря с `__iter__()` - выдающая итератор. Итератор - это одноразовый курсор с `__next__()` (выдает элементы по одному и бросает `StopIteration`) и `__iter__()`

Как работает цикл `for`? Вызывает `iter()` у объекта и крутит `while True` с `next()`, пока не поймает `StopIteration`

Чем `yield` отличается от `return`? `return` - завершает функцию и стирает ее стек, а `yield` - замораживает выполение функции, сохраняя все ее локальные переменные, отдает значение по запросу `next()`

Что возвращает `(x for x in range(10))` Не кортеж, а ленивый объект-генератор (`Generator Expression`), занимающий O(1) памияти

Зачем нужен `yield from`? Для делегирования управления вложенному итератору/генератору напрямую



# Устройство памяти в Python: Объекты, Ссылки, Копирование и GC

1. Переменные, объекты и `PyObject`
Главная метафора (Склад и ярлычки): В отличие от C / Pascal, в Python переменная -это не коробка со значением, а бумажный ярлычок (ссылка), привязанный веревочкой к реальному объекту на складе оперативной памяти (Heap)

Что хранит каждый `PyObject` в CPython:
Само значение
Указатель на тип объекта (так работает динамическая типизация)
Счетчик ссылок `ob_refcnt` (сколько ярлыков сейчас привязанно к объекту)
Присваивание (`b = a`): Объект не копируется, просто к той же коробке в RAM привязывается новый ярлычок

2. Операторы `is` против `==` и кэш чисел

`==` (Equality/Равенство значений) сверяет содержимое самих коробок (под капотом вызывает дандер метод `__eq__`)

`is` (Identity / Тождественность по адресу): сравнивает не значения, а адреса в памяти (`id(a) == id(b)` - ведут ли веревочки к одной и той же коробке)

Почему правильно писать is None: потому что None реально существующий объект-синглтон в едиственном экземпляре на весь процесс.
Провера через `is` работает многовенно и ее нельзя переопределить как `__eq__`

Кэш малых чисел (Small Integer Caching): при старте `CPython` заране создает числа от `-5` до `256`. Сравнение чисел через `is` опасный баг: на числах из кэша оно может случайно вернуть `True`, а числа за пределами кэша (например `1000` и созданный в рантайме `int("1000")`) значения равны (`==` даст `True`, а проверка через `is` вернет `False` так как разные адреса в памяти)

3. `mutable` и `immutable` и ловушки мутабельности

Неизменяемые (`immutable`): `int, float, str, bool, frozenset, tuple.` Любая модификация создает новый объект в памяти и перевешивает ярлык на новый `id()`

Изменяемые (`mutable`): `list, set, dict.` Кастомные классы, меняются сразу на месте без смены `id()`

Миф про абсолютно неизменяемй `tuple` кортеж: кортеж хранит в себе ссылки на объекты в памяти при попытке изменить ссылку вылетит ошибка `Type Error` - (изменить элемент по индексу нельзя), но важно понимать что если элементом кортежа является список `list`,то его можно изменять с помощью `.append()`. Такие (`нехэшируемые`) кортежи нельзя передать как ключ словаря или элемент множества. 

Коварство операций `+=` и `+` над списками `list`
`+=` работает по принципу функции `.extend()`, что изменяет уже существующий объект ячейки памяти, все переменные ссылающиеся на этот объект тоже увидят эти изменения
`+` создает новый объект в памяти

Какая проблема возникает, если аргумент-поумолчанию мутабельный `def funct(a=[])`
Это приводит к тому что список создается один раз при чтении, последущие исполнения функции будут класть элементы в общую корзину
Решение: аргумент по умолчанию `None`, а уже в теле функции вызывать проверку на `is None` и создавать пустой список `list = []`

4. Поверхностное и глубокое копирование `copy()` vs `deecopy()`
Главное отличие: `copy` создает поверхностную копию, если состав объекта входят вложенные структуры, то их изменение затронет объект оригинала
Функция `deecopy` позволяет создать клона, изменения которого никак не затронут исходный объект, но важно понимать что частое использоване нагружает CPU (`memo` - для запоминания ссылок уже скопированных объектов) и RAM, поэтому используется точечно

5. Управление памятью в CPython. `Reference Counting` и `gc (Garbage Collector)`
Правило del: del удаляет на сам объект а отрывает один ярлычок и уменьшает количество ссылок на 1, пока на объект смотри другая переменная, он продолжает жить

1 уровень Подсчет ссылок (`Reference Counting`)
Главный принцпи работы, видит что количество ссылок на объект - 0, сразу же удаляет его, бессильная если объекты ссылаются друг на друга или объект ссылается сам на себя, количество ссылок не при каком условии не упадет в ноль (Аналогия, переменные - отдельные острова которые мостами связываюстя с переменными на материке (объекты в ячейках RAM), функция del удаляет мосты между переменными и объектами, но не между самими островами, возможен случай когда переменная держит сама себя за воротник)

2 уровень Циклический сборщик мусора `gc - Garbage Collector`
Следит только за контейнерными объектами (`list, set, dict, tuple`) существуют для поиска и сноса недостижимых извне циклических островов

Гипотеза выживаемости и 3 поколения (Gen 0, Gen 1, Gen 2) - большинство объектов умирает быстро, поэтому свежепоявивщееся контейнеры поколения (`Gen 0`) проверяются чаще всего, а долгожители пережившие прошлые проверки переходят в поколения (`Gen 1` и `Gen 2`) и проверяются все реже чтоюы не тормозить программу лишними паузами `Stop-the-World`
`gc.get_count()` показывает не количество мусора, а счетчик новых/проверенных объектов в поколениях до следующей автоуборки
`gc.collect()` запускает полную ручную сборку и возвращает число уничтоженных объектов



# Асинхронность, Конкурентность vs Параллелизм

1. `Конкурентность` это свойсвто характеризующее то, как потоки процессора выполняют задачи (передают эстафету друг другу)
   `Параллелизм` это свойство при котором выполняемые действия выполняются одновременно (все расчеты идут одинаково)

    Какие задачи могут стоять перед разработчиком?
    `CPU-bound` и `I/O-bound`, задачи первого типа подразумевают что все действия осуществляются системой (производится сложные вычисления и рассчеты), вторые же не просто вычисляют, а отправляют и принимают данные других систем
    Если рассматривать с точки зрения конкурентности и параллелизма, для решения вторых задач требуется использовать несколько потоков процессора, которые будут конкурентно исполняться, а действия внутри них буду выполняться параллельно, либо же `asycio` (один поток), если позволяют библиотеки

2. `GIL `(Global Interpretetor Lock) - механизм интерпретатора который регулирует выполнение действий потоками (передача эстафеты), поддерживает корректную работу памяти вцелом (следит за `ob_refcnt`), задачи типа `CPU-bound` c `GIL` могут выполняться даже медленнее чем их поочередный запуск внутри одного потока, из-за передачи эстфаеты друг другу.
Задачи типа `I/O-bound` наоборот выполняются намного быстрее, потому что потоки действуют конкуретно, доходя до точки ожидания они кладут GIL на полку, другие потоки повторяют эти же действия.
`start()` - разветвляет основной поток (поезд) на две ветки со своими потоками (поездами), `join()` соединяет все поезда на отходящих ветках в один, который идет дальше по программе

3. `Race condition` - состояние гонки, случайь когда две функции на разных потока меняют значения переменных, что может привести к неточным вычислениям. Почему это происходит: потому что `GIL` (эстафета) передается каждые несколько милисекунд между потоками, в таком случае тот от кого была передана эстафета застывает, другой поток меняет переменные, происходит передача, выполение застывшего потока продолжается с места остановки (он не видит изменения в переменных), для этого используется блокировка потоков (`threading.Lock`) - замок на данные, которыми оперирует функция исполняемого потока - это назвается `Mutex` потока (блокирует доступ к тем переменным, которые меняются другим потоком). `Deadlock` это состояние когда нужные переменные для первого потока заблокированы вторым, а переменные для второго заблокированны первым (БЕСКОНЕЧНОЕ ОЖИДАНИЕ)

4. `Multiprocessing`
`Multiprocessing` - способ организации при котором функции исполняемые в одном файле разделяются на несколько процессов (со своей памятью и `GIL`) - реальный параллелизм. Самый лучший вариант для решения задач типа `CPU-bound`. Важно помнить что создание новый процессов в Python нужно контролировать, чтобы они не плодили другу друга до бесконечности и интерпретатор не выкинл ошибку `Runtime Error`. (Решение: конструкция `if __name__ == "__main__"`)

5. Asyncio Асинхронность
Корутины `async` и `await` + `Event Loop` (Цикл событий) - позволяют достичь конкуретности выполнения внутри одного потока процессора (конкурентны в данном случае сами задачи), ключевое слово `await` говорит циклу событий что поток свободен и готов исполнить новое указание, корутины это прямой потомок генераторов (`yield`). если внутри функции передавть исполнение через несколько одинаковых строк, начинающихся с `await`, то `Event Loop` будет выполнять эти действия последовательно, для корректного запуска используется одно слово `await` и функция `gather` в аргументы который передаются нужные функции. Важно помнить что корутины и `Event Loop` дружат только с асинхронными библиотеками, при попытке использовать в асинхронной функции синхронные модули или библиотеки все будет выполняться последовательно на одном ядре (Самый наихудший вариант из всех имеющихся)

6. Заключение (Что и где применять):
`CPU-bound` - использовать `multiprocessing`
`I/O-bound` (с блокирующими библиотеками) - `multithreading`
`I/O-bound` (асинхронные библиотеки и модули) - `asyncio`
